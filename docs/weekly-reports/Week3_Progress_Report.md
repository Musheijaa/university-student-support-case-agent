## 1. Project Overview and Context

Week 2 delivered a working foundation-model baseline: a FastAPI backend that sends a student's question to Groq through a versioned prompt (V1.0, V2.0) and returns a structured response, with no source of university-specific knowledge beyond the model's own training. Week 3's objective, per the brief, was to make the application answer from a controlled, traceable knowledge source instead of relying on model memory — i.e. retrieval-augmented generation (RAG) with source grounding — while keeping the Week 2 baseline fully intact and extending it rather than replacing it.

## 2. Work Completed

The following deliverables were completed during Week 3:

- Ingested a controlled corpus of real, public Makerere University policy documents (`docs/makerereUniversityPolicyDocs/`) — text extraction, chunking, embedding, and indexing implemented in `agent-backend/rag/` (`loader.py`, `chunker.py`, `embeddings.py`, `vector_store.py`).
- Assigned every corpus document a stable `DOC###` id with provenance metadata in `agent-backend/rag/corpus_manifest.py`, documented for the team in `docs/corpus-source-register.md`.
- Implemented semantic retrieval (`retriever.py`) with a configurable top-k and a minimum-similarity threshold, and a context-construction step (`context_builder.py`) that builds the model's evidence block and the API's `sources` field from the *same* retrieval results — sources are generated by the application from real metadata, never by the model, so a citation cannot be fabricated.
- Added a new versioned prompt, `rag-v1.0`, that instructs the model to answer only from supplied evidence and say so when evidence is insufficient — added alongside V1.0/V2.0, not replacing them.
- Extended `POST /api/v1/student-support` to run retrieval before generation and return a `sources` array; the response schema change is additive, so Week 2 behavior (verified via the existing test suite) is unaffected.
- Wrote an `ingest.py` CLI to build/rebuild the vector index from the corpus, and a `chat_cli.py` terminal client for manual testing.
- Discovered, during ingestion, that 6 of the original 18 corpus PDFs were scanned/image-only with zero extractable text (confirmed directly via `pypdf`) — removed them from the corpus and the manifest rather than leaving dead, silently-unsearchable files in the repository (see `docs/corpus-source-register.md`).
- Ran and recorded 15 real RAG evaluation cases (answerable / partially answerable / deliberately unanswerable) against the live corpus and Groq API — `docs/rag-evaluation.md`. No result was fabricated; cases that couldn't be run yet would have been marked `BLOCKED`, not guessed.
- Found, evidenced, and documented 4 real retrieval/grounding failures with root causes and potential fixes — `docs/rag-failures.md`.
- Added 20 new automated tests covering chunking, context building, retrieval filtering, loading, and the vector store, all running against local fixtures or a real-but-cached local embedding model — no test depends on a live paid API call except the one pre-existing opt-in Groq integration test.

## 4. Key Engineering Decisions and Rationale

**Embedding model — local ONNX over hosted API or PyTorch:** rather than adding a hosted embeddings API (recurring cost, another API key) or `sentence-transformers` (which pulls in PyTorch, ~1-2GB), the pipeline uses ChromaDB's built-in default embedding function — a small MiniLM ONNX model run locally via `onnxruntime`. No API key, no per-call cost, and it's isolated behind `rag/embeddings.py` so it can be swapped later without touching the rest of the pipeline.

**Corpus cleanup over silent partial ingestion:** when 6 of 18 PDFs turned out to be scanned images with no extractable text, the team chose to remove them from the corpus and manifest rather than leave them in the repository looking like part of the knowledge base while silently contributing zero chunks. This keeps the corpus register honest about what the system can actually answer from.

**Retrieval threshold calibrated empirically, not guessed:** `RAG_MIN_SCORE` was set by running real queries against the real corpus and inspecting actual similarity scores (0.35, chosen because it separates genuinely relevant matches ~0.37+ from clearly-irrelevant ones ~0.28-0.31) rather than picked arbitrarily — and even so, evaluation surfaced cases where it isn't strict enough (see `docs/rag-failures.md`, Failure F2).

**Extend, don't replace, Week 2:** the V1.0/V2.0 prompts and the non-RAG code path remain fully functional and tested; RAG is a new prompt version (`rag-v1.0`) and a new retrieval step ahead of generation, not a rewrite. This was verified directly, not assumed: the full Week 2 test suite plus a manual call using the legacy `v2.0` settings both still pass.

## 5. RAG Pipeline Summary

| Stage | Implementation |
|---|---|
| Corpus | 12 real Makerere policy PDFs, `docs/makerereUniversityPolicyDocs/` |
| Ingestion / text extraction | `pypdf`, per-page, `agent-backend/rag/loader.py` |
| Chunking | Fixed 1000-char chunks, 150-char overlap, never crosses a page boundary, `chunker.py` |
| Embeddings | ChromaDB default ONNX MiniLM, local, no API key, `embeddings.py` |
| Vector store | Persistent ChromaDB collection, cosine distance, `vector_store.py` |
| Retrieval | Top-k=4, min similarity 0.35, `retriever.py` |
| Context construction | Evidence block + deduplicated source list built from retrieval metadata, `context_builder.py` |
| Generation | Groq (`openai/gpt-oss-20b`), prompt `rag-v1.0`, `llm/service.py` |
| Response | `{response, prompt_version, model, sources[]}` from `POST /api/v1/student-support` |

## 6. Failures, Challenges, and Current Response

Four real retrieval/grounding failures were found and documented in `docs/rag-failures.md`:

1. **Corpus coverage gap** — 6 of 18 PDFs unreadable (no OCR in this pipeline). *Response: removed from the active corpus, documented, OCR proposed for a later phase.*
2. **Weak-relevance sources shown for off-corpus questions** — irrelevant chunks sometimes score above the similarity threshold. *Response: documented with real scores; the model's own answer stayed safe in every case, but the `sources` field can be misleading; re-ranking or a stricter threshold is proposed for later.*
3. **Duplicate corpus document not deduplicated** — two files for the same Research Policy. *Response: documented; content-hash deduplication proposed for a later ingestion pass.*
4. **Chunk-boundary truncation** — fixed-size chunking cut one clause mid-word. *Response: documented with the literal truncated text; the model itself flagged the gap rather than guessing, but semantic-boundary-aware chunking is proposed as a fix.*

None of these caused a hallucinated or unsafe answer in testing — the `rag-v1.0` prompt's instruction to say so when evidence is insufficient held up in every case checked — but all four are real, currently-unfixed weaknesses, not resolved risks.

## 7. Risks Going Into Week 4

- The corpus has no readable source at all for fees, accommodation, teaching/learning policy, ODeL, grants, or semester-credit regulations, since those documents were unreadable and removed — any Week 4 feature that assumes broader policy coverage will hit this gap.
- The `sources` field can include weakly-relevant documents even when the answer correctly declines (Failure F2); if Week 4 surfaces sources more prominently in a UI, this should be tightened first.
- No re-ranking or query-rewriting step exists yet; retrieval quality is sensitive to how a question is phrased (observed directly: RAG-07 vs. the broader exam-malpractice question retrieved different, better evidence for a more specific phrasing).
