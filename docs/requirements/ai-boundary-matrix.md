# AI Boundary Matrix

| Capability | AI Role | Deterministic Role | Human Approval Required? | Reason/Boundary |
| --- | --- | --- | --- | --- |
| Understanding student questions | Interprets natural-language requests and identifies likely intent | Validates whether the request is within the supported academic-support domain | No | AI can help with language understanding, but the supported domain remains bounded and clearly defined. |
| Retrieving relevant information | Finds candidate passages or policy notes from approved documents | Confirms that the source material is approved, relevant, and within the allowed scope | No | Retrieval should be limited to curated university/course documents or synthetic materials approved for the project. |
| Generating explanations | Summarizes guidance in accessible language and suggests next steps | Ensures the answer is grounded, not fabricated, and does not exceed policy boundaries | No | AI can explain approved rules, but it must not invent or extend policy beyond the source text. |
| Checking simulated case status | Interprets a case-status request and frames the query | Validates identity, permissions, and the existence of a matching case record | No, unless a case is outside allowed access or requires human escalation | A status lookup is a bounded operational workflow and should be implemented through deterministic rules. |
| Checking simulated timetable information | Interprets requests about course schedule information | Validates identifiers and returns only allowed data from the simulated dataset | No | The domain is controlled and limited to simulated, non-production academic information. |
| Validating inputs | Helps identify missing or ambiguous fields in user requests | Enforces required fields, data types, and business rules before action is taken | No | Validation is a deterministic software responsibility; AI should not be the source of truth for data integrity. |
| Authorization | May suggest whether a request appears authorized or requires further review | Enforces access rules, identity matching, and role/permission checks | Sometimes | If the user is trying to access non-permitted records, deterministic logic must block the action. |
| Creating a simulated support ticket | Drafts structured case content and summarizes the issue | Creates the final support ticket record, assigns identifiers, and stores status | No | Ticket creation is a controlled internal workflow, not a high-impact decision. |
| Routing a ticket | Suggests likely route based on the issue type | Applies the final routing logic according to predefined business rules | No for routine cases, yes for exceptions | Routing is deterministic; AI can support triage but the decision remains controlled by software rules. |
| Escalation | Identifies when a request may need escalation or human support | Decides whether the case qualifies for escalation based on policy and rule checks | Yes | Escalation is not an AI decision. It requires human review because it may impact student outcomes or operational risk. |
| Sensitive/high-impact decisions | May classify a request as potentially sensitive | Prevents action if the request touches grading, fees, disciplinary action, legal, or medical domains | Yes | These categories are explicitly excluded from the project’s bounded scope and require human approval. |
| Handling off-scope questions | Detects unsupported questions and politely declines | Returns a safe refusal message or triage path | No | AI may recognize the boundary, but the decision to continue or escalate stays controlled. |

## Boundary Summary
The project follows a simple rule: AI supports interpretation, guidance, and workflow assistance; deterministic software validates, authorizes, stores, routes, and restricts actions; humans review escalation and any request that touches a high-impact or sensitive area. This keeps the prototype safe, controllable, and academically appropriate for an 8-week capstone.
